# PD — Does global recording survive the master becoming a Strip?

*Design probe, 2026-07-24. Question asked: if the master stops being `MasterSection` and
becomes `Strip(source = busTap(bus 0))`, autogenerated at session start, does
**global recording** still work — and does it get better or worse?*

*Inputs read: `docs/DECISIONS.md` D-WZ-GREC-01 · D-WZ-DECK-01 · D-WZ-CORE-02 ·
D-WZ-RECMODEL-01 · Law C-2 · `docs/specs/global-recording.md` ·
`docs/specs/recorder.md` §§4–5, §9 · `docs/specs/playback-composer.md` §2 ·
`docs/specs/pd-merge.md` §1 · `engine/src/wz_engine.cpp` ·
`engine/include/wz_engine.h` · `host/src/RecordService.cpp` · `host/src/WavWriter.cpp` ·
`shell/src/Main.cpp` · `web/src/plane/Strip.tsx` · `web/src/engine/usePatch.ts` ·
`web/src/store/appStore.ts`.*

**Verdict up front.** The idea is *half* right, and the half that is right is the smaller
half. A Strip should be able to record a bus — that is a real, small, worth-building
engine change, and it makes "resample the mix into a deck" a first-class verb. But
**global recording must not be that strip**. Three independent walls stop it: the RAM cap,
the deck count, and the self-recording feedback path. Making the master a Strip does not
improve global recording; it would quietly delete the archivist and leave an instrument
wearing its name.

---

## 1. Can a Strip record a BUS today? No — and the code says so out loud

`wz_engine.h` is explicit:

> `/* --- deck recording (P3) --- The deck records `channels` ENGINE-input channels
> (chan0 = L/mono, chan1 = R or -1) into its buffer` */

and the render pass (`wz_engine.cpp`, deck RECORD pass) resolves the source as:

```
const float* r0 = (in_bus != nullptr && d.recSrcChan0 >= 0 &&
                   (uint32_t)d.recSrcChan0 < in_count) ? in_bus[d.recSrcChan0] : nullptr;
```

`in_bus` is the *device input* array from `wz_engine_render_io`. There is no other record
source. The UI already models this honestly: `recordChannels()` in
`web/src/plane/Strip.tsx` returns `null` for `busTap` (and for `appTap` /
`systemMixExcept` / `virtualDeviceInput`), which disables the record verb **with the
reason printed in the tooltip** — "the engine captures input channels, and `busTap` names
none". `web/src/plane/recordChannels.test.ts` pins that as a test. This is
D-WZ-RECMODEL-01 step A working exactly as designed: the gap is visible, not silent.

### What is missing, minimally

One new record-source kind: **a bus, not an input channel**.

```c
/* -1 = none. 0 = main, 1 = monitor (the buses the LoopbackBus snapshots). */
void wz_deck_set_record_source_bus(wz_engine* e, uint32_t deck, int32_t bus);
```

The signal is *already there and already sample-aligned*. `wz_engine_render_io` keeps
`loopbackMainL/R` and `loopbackMonL/R` — the previous block of each bus, snapshotted
**after the master fader and after the watchdog limiter**, i.e. exactly "what left the
app". The deck record pass runs at the *top* of the block, before the mix overwrites
anything, so at record time those arrays still hold block N−1. The change is:

- `deck.h`: one `int32_t recSrcBus = -1;` field.
- `wz_engine.cpp` record pass: `if (d.recSrcBus >= 0) { r0 = loopbackMainL.data(); r1 =
  loopbackMainR.data(); }` (or the monitor pair), and force `ch = 2`.
- `wz_engine.h` + the schema/dispatch pair in `shell/src/Main.cpp` (`deckRecordStart`
  gains an optional `bus`).
- `recordChannels()` in `Strip.tsx` returns a bus descriptor for `busTap` instead of
  `null`; the disabled-with-reason path stays for `appTap` and friends.
- One fixture: record a bus while a known tone plays, assert the take equals the bus
  output delayed by one block.

**Honest size: small. ~40 lines of engine + ABI, a day including the fixture.** It is not
architectural. Three caveats that are *not* optional:

1. **The stamp is one block early.** `d.recStartSample = blockStartSample`, but the audio
   captured in that block is block N−1's. A bus take's honest stamp is
   `blockStartSample − loopbackFrames`. Get this wrong and every bus take is ~2.7 ms
   (128 fr) to ~10.7 ms (512 fr) ahead of every input take — a device-dependent error,
   the worst kind. Fix it at the stamp, not in the UI.
2. **Only buses 0 and 1 exist as snapshots.** Buses 1..7 are written straight to device
   channels (`accBusL[b] * smMain`) and never snapshotted. "Record any bus" needs seven
   more snapshot pairs — still small, but it is a new allocation and a new per-block copy,
   so scope it deliberately.
3. **The snapshot is only as good as `bus_out`.** `loopbackMain*` copies from `bus_out[0]`
   / `bus_out[1]`; with a device that presents fewer than two output channels the
   snapshot is zeros. A bus recording on a mono/absent output device records silence and
   must say so.

## 2. Does D-WZ-GREC-01 survive? No. It is violated on all three clauses

D-WZ-GREC-01: *"Global capture is **file-only**: no RAM buffer, no 256 MB cap, not
live-loopable — the archivist, not the instrument."*

A Strip recording is the exact negation of each clause, by construction, not by accident:

| D-WZ-GREC-01 says | A Strip record does | Where |
|---|---|---|
| no RAM buffer | the record buffer **is** the playback buffer | recorder.md §1; `d.appendFrame` |
| no 256 MB cap | `recCapFrames = 256 MiB / (ch·4)`, hard | `wz_deck_record_start` |
| not live-loopable | Law C-3 makes it loop **in the same block** | record pass, `arm == 2` |

These are not reconcilable by adjusting a constant. They are reconcilable only by
inventing a **strip variant that has no RAM buffer** — at which point it is no longer "the
machinery every other strip already has", it is a second recording path wearing a Strip
costume, and the appeal of the proposal has evaporated.

**Which should change — the decision or the design?** The decision. But not the way the
proposal wants.

D-WZ-GREC-01 is right about *what global recording is*: an archivist. Its rationale
("make the cost optional at the moment it is incurred") and its Law C-2 extension are
sound and I would not reopen them. What the proposal legitimately exposes is a **gap the
decision did not address**: there is no verb for *"capture the mix as playable material"*.
Today the only way to get the mix into a deck is a `busTap` strip you cannot record.
That gap is real, and it is what §1 fixes.

So: **the decision does not change; the design gains a sibling.** Global record (archive,
file-only, uncapped) and bus-record-into-a-strip (instrument, RAM, loopable, capped) are
two different verbs that happen to tap the same signal. Merging them loses one of them.
Naming both is the honest outcome, and it costs one sentence in D-WZ-GREC-01's
consequences rather than a re-signature.

## 3. The 3-hour set — where master-as-strip stops being an argument

Numbers, computed from the code and not from the prose:

- `wz_deck_record_start`: `recCapFrames = (256 MiB) / (channels · 4)`. **Stereo: 33,554,432
  frames = 11 min 39 s at 48 kHz.** Mono: 23 min 18 s.
- **Flag:** D-WZ-DECK-01 and `recorder.md` §1 both say "≈ 23 minutes of stereo float32 at
  48 kHz". That is the **mono** figure. The stereo cap is *half* the documented one. The
  code is right and the prose is wrong; worth a correction pass, and it matters here
  because it halves the only number anyone will reason with.
- A 3-hour stereo set in RAM would be **3.86 GiB** — 11.9× the per-deck cap and ~2× the
  whole 8-deck budget D-WZ-DECK-01 was chosen to bound.

So what happens if you press record on a master strip at the top of a 3-hour set? At
11:39 the render pass hits `pos >= d.recCapFrames`, sets `recCapReached`, and stores
`DeckState::idle`. Recording stops. **The drain stops with it** — the drain write is
inside the same loop, after the `break`. The file therefore ends at 11:39 too. The
archivist has archived 6% of the set and the lamp says so in a corner. That is the worst
possible failure for the one use case global recording exists for.

The three options, weighed:

1. **A strip variant that drains to file with no RAM buffer.** Technically the right
   audio design — and it is *literally what `GlobalRecordService` already is* in
   `global-recording.md` §6. Building it "as a strip" adds a Strip object, a document
   field, a UI state ("this strip has been recording for 3 hours and has nothing to
   play"), and a second meaning for the record button, in exchange for zero reuse: the
   deck buffer, the Law C-3 handoff, the cap service, and the material/monitor swap all
   have to be *disabled* for it. Negative reuse.
2. **Let the cap stop it.** Rejected outright. Silent-ish truncation of a 3-hour archive
   is the failure D-WZ-DECK-01's "never glitches under memory pressure" rationale was
   protecting *decks* from, applied to the one thing that must not be bounded.
3. **Keep global recording separate from strips.** The drain ring is already the shared
   part. `wz_deck_drain` → `RecordService` → `WavWriter` needs no deck buffer at all — a
   global tap can write into a `SourceRing` from the render and be pulled by a service
   thread on exactly the P3 pattern, with no `Deck` involved.

**Recommendation: option 3.** Global recording stays its own service. The reuse the
proposal was reaching for is *real* but it lives one layer down — in the drain ring, the
`WavWriter`, and the stamp — not in the Strip. Reuse the plumbing, not the object.

There is a fourth wall, independent of RAM: **`kMaxDecks = 8`**. `attachDeck` returns −1
when they are gone. A master strip that records burns one of the eight decks the looper is
made of, permanently, for a strip whose material you never want to play.

## 4. MULTITRACK — "arm them all" does not produce what D-WZ-GREC-01 promised

It is tempting, and it is wrong in four distinct ways.

1. **Wrong tap point.** D-WZ-GREC-01/`global-recording.md` §4 specify per-strip capture as
   *"that strip's post-fader contribution"*. A deck record captures `in_bus[chan]` —
   **pre-fader, pre-pan, pre-mute, pre-solo**. Arming every strip produces a *dry input
   archive*, which the spec explicitly puts out of scope ("a pre-fader tap would be a new
   decision"). Same button, different product.
2. **Most strips cannot be armed at all.** `recordChannels()` returns `null` for `appTap`,
   `systemMixExcept`, `virtualDeviceInput` and `busTap`. Those are precisely the
   *"streamed-through material that never touches a deck"* that §3 of the spec names as
   the reason multitrack exists. Arm-them-all captures everything except the material the
   mode was invented for.
3. **Eight decks, N strips.** Multitrack is defined over *every active strip*. Strips are
   unbounded; decks are eight. The mode cannot express its own definition.
4. **The cap again.** Every armed deck stops at 11:39, independently, at slightly
   different moments. Eight files of eight different lengths.

**Is the common origin free?** The *law* is free. The *implementation is not — and it is
broken today.* Tracing it end to end:

- `WavWriter::open` writes `TimeReference` (u64) into `bext` at offset 338 from the
  value passed in. Correct, and `wav_killtest` proves it with 123456789.
- `shell/src/Main.cpp`, `deckRecordStart`:
  `recorder.beginTake(deck, ..., 0 /* stamped by the engine */, desc)`.
  **Zero is passed.** The header is written once at open and `TimeReference` is never
  patched afterwards (`close()` patches only the RIFF/ds64 size fields).
- `RecordService::endTake` then writes the sidecar from `slot.startEngineSample` — still
  that same 0.
- `RecordService::drainDeck` calls `wz_deck_drain(..., &stamp)` and **discards `stamp`**;
  the engine's real `recStartSample` is available on every drain tick and thrown away.
- `usePatch.deckRecordStop` receives the correct `r.startEngineSample` in the reply and
  ignores it, calling `addTake(r.take)` — the RecordService record, stamped 0.

**Consequence: every shipped take carries `TimeReference = 0` and
`"startEngineSample": 0`.** The DAW lays them all at 00:00:00. `alignedStartSample`
subtracts two zeros and aligns nothing. Law C-2 is correct as a law, correct in the
engine, correct in the writer, and severed at exactly two joints in between.

*Unverifiable from reading alone:* `engine/tools/deck_stamp_test.cpp` presumably proves
the engine-level delta (it is an engine tool and never touches a file), and
`wav_killtest.cpp` proves the writer. **No test covers the shell → RecordService →
sidecar hop, which is where the value is lost.** I did not run the suite; someone should
confirm by recording two takes and reading the two sidecars.

**This is the single most valuable finding in this document, and it is entirely
independent of master-as-strip.** Fix it first — it is roughly: keep the first non-empty
drain's `stamp` into `slot.startEngineSample`, patch the 8 bytes at
`bextDataPos + 338` at `close()`, and add a fixture asserting two staggered takes'
`TimeReference` delta equals the real gap. Until that lands, "multitrack for free" is a
claim, not a capability — and building anything on top of it inherits the zero.

## 5. The self-recording paradox — the master strip is a feedback loop, not a master

This is the part that kills the proposal on audio grounds rather than bookkeeping ones.

**The routing fact.** A Strip's output goes to `ch.outBus`, and the render clamps it:

```
const uint32_t ob = (ch.outBus >= 0 && ch.outBus < kMaxOutBuses) ? ch.outBus : 0u;
```

There is **no "routed nowhere"**. An unrouted strip lands on bus 0. So
`Strip(source = busTap(0))` with default routing is, verbatim:

> `bus0[N] += bus0[N−1] · stripGain · masterFader`

A recirculating one-block delay line. At unity that is a sustained runaway; below unity it
is a dense comb at the block rate (128–512 samples ⇒ 375–94 Hz). The `watchdog` (250 ms
leaky RMS, ramped ceiling) would engage and *hold the level* — so the recording would not
clip, it would just be wrong, quietly, at a controlled loudness. The codebase already
knows this: `appStore.addLoopback` creates every loopback strip **muted**, with the
comment *"an unmuted unity loopback of main is an instant sustained feedback path"*.

**So for the recording to be the mix the user actually heard, all of the following must
hold:**

1. The master-record strip contributes **exactly zero** to bus 0 — not "faded down".
   `mute` reaches exact zero only after the 10 ms raised-cosine ramp completes, so a mute
   toggled at record time leaks 10 ms of recirculation into the take. It must be zero
   *before* the tap exists, or the strip must be structurally incapable of feeding a bus.
2. `toMonitor` is false, or the cue path acquires its own loop through `loopbackMon`.
3. **It never plays back into the mix.** This is the fatal one. `usePatch` swaps a strip's
   source to its material whenever `ch.material && !ch.monitorSwitch`; Law C-3 has the
   deck **looping in the same block as record-stop**. So the instant you stop the master
   record, the strip becomes a deck strip playing 11 minutes of the set back into bus 0 at
   full level — and it is now also in the next recording. The archivist becomes the loudest
   instrument on stage at the moment the set ends. D-WZ-ARRIVAL-01 chose "material arrives
   stopped" precisely to prevent software making sound nobody asked for; Law C-3 is its
   one signed exception, and it fires here.

**Does the one-block delay save us?** It makes the cycle *legal and analyzable* — it is
why this can be discussed at all instead of being a stack overflow. It does not make it
*inaudible*. One block of delay is the mechanism of the feedback, not a defence against
it. What the one-block delay genuinely buys is the good half: because the record pass runs
before the mix and reads the same `loopbackMain*` array the `busTap` playback path reads,
a bus recording and a bus monitor are **sample-aligned with each other**, and the take is
post-master-fader and post-limiter — i.e. genuinely "what left the app", exactly the tap
point `global-recording.md` §1 asks for.

**Conclusion for §5:** a strip that records the sum is safe only if it is *not a strip* in
the one respect that defines strips — that they feed a bus and play their material. A
"strip" with no bus output and no playback is a service with a rectangle drawn around it.

## 6. Recommended shape

**Build (in this order):**

1. **Fix the Law C-2 stamp wiring** (§4). Shell → RecordService → `bext` → sidecar → UI.
   One fixture proving two staggered takes' `TimeReference` delta equals the real gap.
   Everything downstream — align, multitrack, DAW import — is a lie until this lands.
   Independent of every other item here.
2. **Correct the cap prose** in D-WZ-DECK-01 and `recorder.md` §1: 256 MiB is **11 min 39 s
   stereo**, 23 min mono. Also correct `global-recording.md` §4: the writer is 32-bit
   float (`bitsPerSample = 32, floatFormat = true`), so the real cost is **~23 MB/min ≈
   1.38 GB/h per stereo file**, not 17 MB/min — multitrack with 8 strips is ~12 GB/h, not
   9. State the true number or the "cost is stated, not hidden" clause is not honoured.
3. **`wz_deck_set_record_source_bus`** (§1) — a Strip may record bus 0 or the monitor, with
   the stamp corrected by one block, and `recordChannels()` stops returning `null` for
   `busTap`. This is the genuinely good idea inside the proposal: it makes
   "resample the mix into a deck" a real verb and closes a hole D-WZ-RECMODEL-01 step A
   documented but could not fill. It is an **instrument** feature, capped and loopable, and
   it should be described that way.
4. **Global recording stays `GlobalRecordService`** per `global-recording.md` §6: its own
   render-side tap into a `SourceRing`, its own writers, no `Deck`, no cap, no playback.
   Reuse the drain ring, the `WavWriter`, and the stamp — not the Strip.
5. If the master *is* eventually drawn on the map (PD-MERGE-03 currently keeps it fixed and
   off-map, deliberately), the global ● belongs on it as a **surface**, not as the strip's
   record verb. Same pixel neighbourhood, different verb, different tooltip.

**Would NOT build:**

- **Master-as-`Strip(busTap(0))` as the global recorder.** Fails on the cap, on
  `kMaxDecks`, and on the self-recording path. No amount of flag-setting makes a
  RAM-buffered, loopable, capped object into an uncapped file-only archivist.
- **"Multitrack = arm every strip."** Wrong tap point (pre- vs post-fader), impossible for
  the tap strips the mode exists to serve, and bounded by 8 decks.
- **A `recordToFileOnly` boolean on `Deck`.** The tempting middle path. It turns the
  record pass into two code paths sharing one state machine, and D-WZ-DECK-01's guarantee
  ("total RAM bounded and predictable") becomes conditional on a flag. Two objects with
  one clear job each beat one object with a mode bit.
- **Raising the 256 MB cap to cover long sets.** It does not fix the class of problem, it
  moves the cliff, and it trades D-WZ-DECK-01's bounded-RAM property for nothing.
- **A "routed nowhere" `outBus` sentinel** introduced *only* to make the master strip safe.
  If unrouted-means-silent is worth having (it probably is — the current clamp-to-0 is a
  trap), it is its own decision, argued on its own terms, not smuggled in as feedback
  mitigation.

---

## 7. Answer to the question as asked

**Does global recording still work if the master becomes a regular Strip? No — it stops
working, and it gets worse in three measurable ways:** capture ends at 11:39 instead of
never; one of eight decks is consumed for material nobody wants to play; and the sum
acquires a recirculating path that the watchdog can only make quiet, not correct.

**What gets better is a different thing than global recording:** a Strip that can record a
bus. That is worth building on its own merits, this week, at ~40 lines. It should ship
under its own name, and D-WZ-GREC-01 should stand.
