# PD-MASTER-AS-STRIP — can the master be a regular Strip?

*Investigation, 2026-07-24. Answers one question posed by the user: could the master
section be a regular Strip, autogenerated at session start, able to loop and record like
any other? Grounded in the code as it stands at SCHEMA_VERSION 27 / PD-MERGE complete.
Nothing here is signed; §6 is a recommendation for the user to accept, amend or reject.*

**User's words:** *"could this be solved through a regular strip as well? this would be
conceptually close if we'd have a master strip but any strip could be this, modular routing
approach... for ease of tool use the master strip will autogenerate and be routed from
session start so we can work right away but its setting can change and a master strip can
also loop and record (but here is where we need to evaluate as the master needs to record
the sum so looping would interrupt this, think)"*

**Short answer.** The instinct is right and the founding law backs it — but `Strip(source =
busTap(bus 0))` is *not* a master, it is a **resampler**, and the difference is not
philosophical: it is three concrete facts in `wz_engine.cpp` and one in `usePatch.ts`. The
master fader is not a strip fader (it scales **all eight** output buses, after the sum,
before the loopback snapshot). A strip that taps bus 0 and feeds bus 0 is a one-block
feedback comb, not a destination. And a Strip renders **exactly one source**, so the instant
the master strip holds material and plays it, `publishPatch` rebinds it to a deck and it
**stops seeing the sum at all** — the user's "looping would interrupt this" is true, and it
is worse than an interruption: it is a rebind. The honest resolution is a **hybrid** (§6):
master becomes a Strip in the *document and the component*, keeps the engine's output-stage
gain, never sums into a bus, and records through the already-signed global-record path
(D-WZ-GREC-01) rather than through a deck.

## 1. Is `Strip(source = busTap(bus 0))` already a master?

### 1.1 What the master surface actually does today

`web/src/panels/MasterSection.tsx` is 68 lines and does exactly five things:

| # | Capability | Mechanism |
|---|---|---|
| 1 | Main fader | `actions.setMainFader(v)` → `link.paramWrite('mainGain', v)` (`usePatch.ts:243`) |
| 2 | Main + cue meters | `MeterCanvas` over HotFrame scalars `mainPeakL/R`, `monitorPeakL/R` |
| 3 | Feedback lamp | `useAppStore(s => s.feedbackAlarm)` ← HotFrame scalar 3 |
| 4 | dB readout | `faderPositionToDb(mainFader)` |
| 5 | Cue-unavailable note | `deviceInfo.monitorAvailable === false` |

It has **no** mute, no solo, no dim, no mono, no insert, no output-bus choice, no record.
The surface is small. That matters: the proposal's cost/benefit turns almost entirely on
items 1–3, not on a long list of master features we would have to reimplement.

### 1.2 Verdict per capability

| Master capability | As `Strip(busTap 0)` | Why |
|---|---|---|
| **Meter the main sum** | ✅ already possible | A busTap strip's own `mPeakL/R` are computed over the previous block's post-fader output. Within one block (10.7 ms at 512/48k) they are the same numbers as `mainPeakL/R` — *provided the strip's own fader sits at unity*, since strip meters are post-fader (`wz_engine.cpp:1216`). |
| **Meter the cue bus** | ⚠️ small work — **currently broken** | `srcChan0` selects main (0) vs monitor (1) at `wz_engine.cpp:1145`, but `CommandDispatch.cpp` only ever sets `srcChan0` for `deviceInput`. `ChannelState::srcChan0` defaults to `-1` (`engine/src/world.h`), so the `↺ cue` strip offered by `AddStrip.tsx:113` **taps main, not cue**. Real bug, ~2 lines. |
| **dB readout / fader curve** | ✅ already possible | Shared `faderCurve.ts`; `ParamRow` already renders it on every Strip. |
| **Cue-unavailable note** | ✅ already possible | `deviceInfo` is store state, readable from anywhere. |
| **Feedback lamp** | ⚠️ small work, real UX cost | `feedbackAlarm` is a global HotFrame scalar; any component can render it. But the lamp and the main meters must be **always visible**, and a Strip lives on a boundless pannable/zoomable plane — you can pan the master off-screen and never see the alarm. This is the strongest *practical* argument against master-on-the-map, and it is not ideological. |
| **Be the master fader** | ❌ structurally impossible as a plain strip | Three separate reasons, below. |
| **Be "the destination every strip feeds"** | n/a — the master never did this | The destination is `accBusL/R[0]`, chosen per strip by `outBus`. The master section owns a *gain stage on the way out*, not the sum. `pd-merge.md §1`'s "it is the destination, not a source" is imprecise: the **bus** is the destination. |
| **Persist across save/reload** | ✅ **gained**, not lost | `mainGain` is *not in the Patch at all* — `PatchSchema` has no master field, and `MasterSection` holds the position in a React `useState`. **A user's −6 dB master comes back at unity on reload.** Making the master a Channel fixes this for free, because `gain` is a persisted Channel field. This is a genuine argument *for* the proposal. |

### 1.3 The three reasons a strip fader cannot be the master fader

**(a) It is applied at the wrong point in the graph.** A strip's gain scales *its own
contribution* before it lands in a bus (`wz_engine.cpp:1197`). `mainGain` scales the *summed
bus* afterwards (`wz_engine.cpp:1244`). No fader on a strip can attenuate other strips.

**(b) It governs all eight buses, not bus 0.** Lines 1286–1298: buses 1..7 are written to
their device pairs as `accBus[b][i] * e->smMain`. The "main fader" is really an
**output-stage gain for the whole app**. Move it onto a bus-0 strip and every spatial layout
(quad / 5.1 / octophonic — the thing CONCEPT §4 sells) silently loses its master fader.

**(c) It sits upstream of the loopback snapshot and the watchdog.** Order per block is:
sum → `smMain` → watchdog limiter → device buffers → *snapshot for next block's loopback*
(lines 1304–1314). A strip fader lives before the sum; it cannot occupy that slot.

**Conclusion for §1.** A busTap(0) strip is an excellent *bus monitor and resampler*. It is
not a master, and no amount of UI work makes it one, because the master gain is an
output-stage, not a channel-strip, operation.

## 2. The central tension: a master strip that records the sum, and is summed into the sum

### 2.1 Exact render order (`wz_engine_render_io`, `engine/src/wz_engine.cpp:766`)

Per block N:

1. **Deck RECORD pass** (l.792–855) — each recording deck captures from `in_bus[recSrcChan0/1]`,
   i.e. **device input channels only**. Stamps `recStartSample`. Handles the Law C-3
   stop→loop handoff *in this same block* (l.798–820).
2. Zero `accMon` and `accBus[0..7]` (l.857–864).
3. Source-ring ASRC pre-pass (l.871–890).
4. **Deck PLAYBACK pre-pass** (l.894–1115) → `deckOutL/R[d]`. Note l.914–916: a deck in
   `recording` state renders **silence** on this pass.
5. **Channel loop** (l.1124–1221) — each strip resolves its source:
   `deviceInput` → this block's input; `deck` → this block's deck scratch;
   **`busTap` → `loopbackMainL/R` or `loopbackMonL/R`, i.e. the PREVIOUS block's output**
   (l.1141–1151). Applies fader/pan/mute, sums into `accBus[outBus]`, and (if `toMonitor`)
   into `accMon`.
6. **Master fader + watchdog** (l.1242–1281) — `l = accL[i] * smMain`, RMS integrator,
   ramped limiter, write to `outL/outR`; cue written from `accMon` **unscaled by `smMain`**.
7. Buses 1..7 → device pairs, `* smMain` (l.1286–1298).
8. **Loopback snapshot** (l.1308–1314) — copy `outL/outR/cueL/cueR` into
   `loopbackMain*/loopbackMon*`. This is post-fader **and post-limiter**.
9. Peaks published; `engineTimeSamples += frames`.

### 2.2 What happens if a busTap(0) strip is routed to bus 0

The strip reads block N−1's *post-fader, post-limiter* output, multiplies by its own fader,
and adds it back into `accBus[0]` — which is then multiplied by `smMain` again and
snapshotted. That is a delay-line regenerator:

> `y[n] = x[n] + g · y[n−1]` with delay = one block (512 frames = 10.7 ms) and loop gain
> `g = stripFader × mainGain`.

- At the unity detent on both faders (`0.75` → 0 dB, `D-WZ-FADER-01`), **g = 1**: marginally
  unstable. Anything that enters the mix never leaves; level climbs by the input's own
  energy every 10.7 ms.
- At the top of either fader (+6 dB), **g ≈ 2**: +6 dB per block. The watchdog's threshold
  (+6 dBFS RMS sustained 250 ms ≈ 23 blocks — `D-WZ-WATCHDOG-01`) is crossed in a fraction of
  a second.
- Below unity it decays — a comb/flanger with a 10.7 ms tail. Musically interesting. Not a
  master.

**Is the one-block delay safe or merely deferred?** It makes the *schedule* safe — that is
all it was ever claimed to do (`playback-composer.md §2`: "the render schedule stays acyclic
**by construction**"). It says nothing about **level**. Delay makes the cycle *computable*;
it does not make it *bounded*. Boundedness is the watchdog's job, and the watchdog is a
**limiter, not a breaker**: it clamps the output and lights the lamp, but the loop keeps
running. The end state is a permanently limited sustained tone with the alarm lit — not a
crash, not a correctness bug, but a hostile default.

The codebase already made exactly this judgment once: `appStore.addLoopback` creates the
strip **muted**, with the comment *"an unmuted unity loopback of main is an instant sustained
feedback path. The user unmutes deliberately, with the watchdog behind them."* That is the
precedent, and it says a bus-0 tap fed back to bus 0 is an opt-in instrument, never a default.

### 2.3 What happens when that strip PLAYS a loop — the rebind that kills it

Here is the fact that decides the user's question, and it is not in the engine.

`web/src/engine/usePatch.ts:40–44`:

```ts
channels: patch.channels.map((ch) =>
  ch.material && !ch.monitorSwitch
    ? { ...ch, source: { kind: 'deck' as const, id: String(ch.material.deckId), name: ch.name } }
    : ch,
),
```

**MATERIAL WINS AT PUBLISH TIME.** The engine renders exactly one source per channel
(`ChannelState` has one `srcKind`). So the moment a master strip gains material and is not
monitoring, it is published as `kind: 'deck'` — and its `busTap` binding is **gone from the
world**. It stops seeing bus 0 entirely. Main metering on that strip dies. It is not that
looping *interrupts* the recording; it is that **holding material at all un-taps the bus.**

So the user's instinct ("looping would interrupt this") is correct and understates it. In
sequence:

1. Master strip taps bus 0, meters the sum. Fine.
2. Press ● → `recordIntoStrip` (`usePatch.ts:116`) attaches a deck, sets `monitorSwitch =
   true`, publishes, calls `deckRecordStart(deck, chan0, chan1)`. **This already fails**:
   `recordChannels()` (`Strip.tsx:58`) returns `null` for `busTap`, so the REC button is
   `disabled` with the reason *"the engine captures input channels, and 'busTap' names
   none."* The engine agrees — `recSrcChan0/1` index into `in_bus` and nothing else.
3. Suppose we fixed (2). While `state == recording`, the deck's playback pass writes silence
   (l.914–916) — so recording and looping are **mutually exclusive states of one deck by
   construction**, not a policy we could relax.
4. On stop with loop enabled, Law C-3 flips it to `looping` **in the same block** (l.798–820).
   From that block on, its output enters `accBus[0]` — the very sum it just captured. One
   block later that is inside `loopbackMain`, and if it ever records again it records itself
   plus everything, compounding per lap. Frippertronics.

**Feature, bug, or watchdog case?** All three, depending on which object you think you are
holding:

- As **the resampler** CONCEPT §4 promises ("loop it back through a deck → resample the whole
  mix into a new take") this is the *feature*, and the watchdog is its net.
- As **the master** it is a *correctness bug*: the archivist's tape now contains the archive.
  D-WZ-GREC-01 calls the global record "the archivist, not the instrument" precisely to keep
  these apart.
- The watchdog catches only the *runaway* case (sustained > +6 dBFS RMS). A loop at unity
  that merely never decays sits under the threshold indefinitely and is never flagged.

## 3. Post-master-fader: where the snapshot is taken

**Good news — the tap point is already exactly right.**

`wz_engine.cpp:1304–1314`, comment in the source: *"Snapshot the buses for the next block's
LoopbackBus reads. Taken AFTER the master fader so a loopback strip hears what actually left
the bus."* It copies `outL/outR`, the float buffers already handed to the device — which
means it is **post-`smMain` (l.1244) and post-watchdog-limiter (l.1271)**.

So a busTap(0) strip sees **post-master-fader audio**, one block late. That is exactly the
point `global-recording.md §1` requires: *"tapped post-master-fader (the same point P4-03's
LoopbackBus snapshots: what actually left the app)."* No change needed on that axis.

Two consequences worth stating rather than discovering later:

- The captured sum will contain **watchdog limiting** when the watchdog is engaged. That is
  consistent with "what actually left the app", and it is the right call — but it should be
  written down, because it means an archive can be dynamics-processed by a safety device.
- Only **main** and **monitor** have snapshots. `loopbackMainL/R` and `loopbackMonL/R` are
  the only buffers kept (l.105). Buses 1..7 have **no** loopback and therefore no tap and no
  post-fader capture point. A spatial session cannot record its own rear channels through
  this mechanism.

**What actually needs changing is the record path, not the tap side:**

1. `wz_deck_set_record_source(e, deck, chan0, chan1)` and the render record pass take
   **device input indices only** (`in_bus[...]`). No deck can record a bus.
2. Even if we added a sentinel (say `chan0 = -2` ⇒ loopback main), routing the global sum
   through a **deck** contradicts D-WZ-GREC-01 head-on: deck recording is RAM-buffered with a
   256 MB cap (`recCapFrames`, D-WZ-DECK-01) and is live-loopable; global recording is signed
   **file-only, no RAM buffer, no cap, not live-loopable**.

**Minimal honest change:** build `P7-GREC-01` as already specced — a bus-0 drain ring filled
at the same place the loopback snapshot is taken (l.1308), pulled by `GlobalRecordService`
into a `WavWriter`. It is ~20 lines in the render path plus the service, it reuses the P3
drain pattern, and it makes "the master strip records the sum" true **without a deck, without
a cap, and without the loop/record exclusivity problem existing at all** — because global
recording is not a deck and has no transport to interrupt.

## 4. What we would lose, and which guards are ugly

Assume for this section the naive reading: master is an ordinary Channel with
`source.kind = 'busTap'`, `outBus = 0`.

| Concern | What happens | Guard needed | Ugly? |
|---|---|---|---|
| **Solo** | `soloRamp` ducks non-soloed strips **on the bus path** (l.1202). Solo any strip → the master strip is ducked → since it is also feeding bus 0, you lose the regen path, not the mix. In the *terminal* design (§6) where the master is not summed, solo would have to exempt it entirely or soloing anything mutes the app. | Master exempt from `anySolo` ducking. | **Yes — a special case in the render loop's hot path**, i.e. exactly the "special master type" we were trying to delete, relocated into the engine. |
| **Mute** | On a summed busTap strip, mute kills only the regeneration path, not the output — the button lies. On a terminal master it would mean "silence the app", which is coherent but a *different verb* wearing the same letter M. | Either redefine mute for this strip, or don't offer it. | Mild. Redefinition is defensible if labelled. |
| **Cue (C)** | A master strip with `toMonitor` on feeds the main sum into the monitor bus — genuinely useful ("cue the mix"), and it would also make a `busTap(1)` strip audibly circular. | None strictly; document it. | No. |
| **Feedback lamp** | Global scalar, renderable anywhere — but on a pannable plane it can be scrolled out of sight. An alarm you can lose is not an alarm. | Pin the master (fixed dock) or duplicate the lamp in the chrome. | **Yes if we insist master lives on the map.** Not ugly if the master is pinned. |
| **Output map** | Unaffected. `outputMap.main = [0,1]`, monitor `[2,3]` when the device has ≥4 outs — set in `usePatch.ts:45`, independent of any strip. | None. | No. |
| **"every strip feeds main"** | Stays true and is *clarified*: strips feed **buses**; bus 0 is main; the master is not the thing they feed. This part of the user's intuition survives intact. | None. | No. |
| **`outBus` on the master** | There is no legal "nowhere". `outBus` is `0..7` in the schema and clamped to `0..kMaxOutBuses` in `wz_world_channel_set`. A terminal master needs an outBus that means *hardware, no bus*. | New `outBus = -1` (none), honoured by one branch in the channel loop; validated in TS. | Small and clean — arguably the *one* honest new primitive here. |
| **Delete the master** | `removeStrip` would remove the app's gain stage, meters and lamp. | Refuse with a reason (the app's established "no silent silence" posture), or auto-recreate on next publish. | Mild. Refusal-with-reason is already the house style. |
| **Route master to another bus** | Would send the main sum into a spatial bus — a legitimate, if exotic, patch, but from the *terminal* master it is meaningless. | Lock `outBus` on the master. | Mild. |
| **Master fader on buses 1..7** | Lost (see §1.3b) unless the engine keeps its output-stage gain. | Keep `mainGain` where it is. | No — if we take the hybrid. |
| **Watchdog scope** | Already main-only: `wdMeanSquare` integrates `accBus[0] * smMain` and nothing else. Buses 1..7 are unguarded. | Out of scope here, but flagged. | n/a |

**The pattern in that table is the finding.** Every guard we need is a re-statement of
"the master is not a source." Push the master into the Strip type and the specialness does
not vanish — it *migrates*, from a 68-line component into the render loop's solo/sum branch,
where it costs more and is far less visible. `pd-merge.md §1` was right about the conclusion
("it is the destination, not a source") even though its stated reason was imprecise.

## 5. The autogenerate idea

*"the master strip will autogenerate and be routed from session start."*

**Schema.** Three options, in ascending honesty:

1. **Reserved key** — `key === 'master'`. Zero schema change, zero migration, zero version
   bump. Stringly-typed: a user-named strip could collide; nothing validates it; and the
   engine's `ChannelState::key` is a plain label, so nothing enforces uniqueness of meaning.
   Cheapest, and the cheapness is a trap.
2. **A flag** — `role: 'strip' | 'master'` on Channel, default `'strip'`. Explicit,
   validatable (`patchValidation`: exactly one `master`, and it must be `busTap`/terminal,
   and its `outBus` must be the none value). Costs SCHEMA_VERSION 27 → 28 and a named
   migration. This is what `pd-merge.md §2`'s rule ("no new persisted field unless one of the
   four surfaces cannot work without it") would actually permit, since the master surface
   cannot work without knowing which channel it is.
3. **A Patch-level field** — `master: { gain, ... }` outside `channels`. Fixes the missing
   persistence (§1.2) with the least conceptual disruption, but concedes the user's point
   entirely: the master is then explicitly not a strip.

Recommend **(2)** if we go strip-shaped, **(3)** if we do not.

**Migration.** Every existing session lacks a master channel *and* lacks any master gain
(`mainGain` has never been persisted — see §1.2). So the migration is: synthesise a master
Channel at unity (`gain: 0.75`), `role: 'master'`, `source: { kind: 'busTap', id: '0' }`,
`outBus: none`, `mute: false`, `solo: false`, at a defined position. Two hazards:

- **Channel count changes**, so HotFrame block offsets shift. That is safe today — every
  offset is derived via `channelFieldIndex()` and block counts ride WorldPublish — but any
  code caching a strip index across a load would be wrong. `Strip.tsx` and `Inspector` read
  indices from the live patch, so they are fine.
- **Placement.** The v16→v17 relayout caveat (MIGRATION.md, PD-MERGE-05a) applies: hand-made
  arrangements exist now that strips are draggable, so the migration must not relayout. If
  the master is pinned (recommended) this is moot — it never occupies plane geometry.

**"What if the user deletes it."** Three postures, in order of preference:

1. **Refuse, with the reason** — matches the house style everywhere else (unmapped bus chip,
   vanished source, unresolved deck: keep working, say what changed). The `×` on the master
   is simply absent or disabled with a tooltip.
2. **Auto-recreate on next publish** — silently repairs, which is exactly the "hidden state
   change" D-WZ-MON-01 rejects.
3. **Allow deletion, app goes silent** — no.

Note that "routed from session start" is already the default for every strip:
`makeChannel()` sets `outBus: 0`. There is nothing to autogenerate *about routing*; the
autogeneration is only about the master's existence.

## 6. Recommendation

### Hybrid: master-as-Strip in the document and the component, terminal in the engine

**Do:**

1. **Leave `mainGain` exactly where it is** — post-sum, pre-snapshot, pre-limiter, applied to
   all eight output buses (`wz_engine.cpp:1244, 1295`). It is an output-stage gain and that is
   the correct place for it. Do not try to express it as a strip fader.
2. **Make the master a Channel** with `role: 'master'` (§5 option 2), rendered by the **one
   `Strip` component** — satisfying `pd-merge.md §5`'s "one Strip component" law and CONCEPT's
   "everything is a channel" at the level where it actually pays: the document. Its `gain`
   field is bound to `mainGain` (UI binding, zero engine change) and is therefore **finally
   persisted** — fixing a live bug (§1.2).
3. **Give it a terminal output.** Add `outBus = -1` ("none / hardware"): one branch in the
   channel loop that skips bus accumulation while still metering. This is the single new
   primitive this design needs, and it is honest — it is what "destination, not a source"
   means in code.
4. **Pin it.** Fixed dock slot beside the map, not a free item on the plane. The main meters
   and the feedback lamp are safety instruments; an alarm you can pan out of view is not one.
   This is the one place I would refuse the "any strip could be this" framing, and the reason
   is ergonomic, not doctrinal.
5. **Wire ● on the master to global recording**, not to a deck: `P7-GREC-01`'s bus-0 drain at
   `wz_engine.cpp:1308`, file-only, no RAM buffer, no cap, per D-WZ-GREC-01. Then *"the master
   strip records the sum"* is literally true, and **the user's tension disappears entirely** —
   there is no deck transport to interrupt, so looping cannot interrupt recording, because the
   master has no loop.
6. **Keep `Strip(busTap 0)` as the separate, user-created, arrives-muted resampler.** It
   already exists (`AddStrip.tsx:110`). It is the instrument — the thing that loops, records,
   overdubs, varispeeds and re-enters the mix. That is CONCEPT §4's promise and it should stay
   available on every bus we can snapshot. Do not conflate the archivist with the instrument;
   D-WZ-GREC-01 already drew that line and it holds here.

**Do NOT:**

- **Do not let the master sum into bus 0.** It is a one-block feedback comb with loop gain
  `stripFader × mainGain`; at the unity detent that is exactly 1.0 (§2.2).
- **Do not route the master's record verb through a deck.** RAM buffer + 256 MB cap +
  live-loopable is the opposite of every clause in D-WZ-GREC-01, and it re-creates the
  record/loop exclusivity the user correctly worried about.
- **Do not delete `mainGain` from the engine.** Buses 1..7 lose their master fader and spatial
  playback silently regresses.
- **Do not put the master on the pannable plane.** See (4).
- **Do not allow solo, delete, or `outBus` change on it.** Each needs a guard; the solo guard
  in particular would land in the render loop's hot path, which is worse than the 68-line
  component we were trying to delete.
- **Do not adopt the reserved-key hack** (§5 option 1) to avoid a version bump. A stringly
  identified master is a silent-failure generator, and this repo has a migration discipline
  precisely so that it does not have to.

### If the user wants the purer answer anyway

The purest version that is still correct is: **there is no master object at all.** `mainGain`
becomes `bus[0].gain` (and each of the eight buses gains its own output gain, fixing the
buses 1..7 asymmetry as a bonus); the meters and lamp live in the chrome; and a user who wants
a "master strip" creates a `busTap(0)` strip themselves, which is the resampler and is
honestly labelled as such. That is arguably the most faithful reading of "everything is a
channel" — because it deletes the master rather than dressing it as a strip. It costs a bus
object in the schema (buses are not currently modelled at all — `OutputMapSchema` is only a
device-channel map) and it gives up "the master fader is where I expect it" for new users.
Worth putting to the user as the alternative to the hybrid.

## 7. Bugs and gaps found while investigating (all verified in code)

1. **`↺ cue` loopback strips tap MAIN, not cue.** `CommandDispatch.cpp` sets `srcChan0` only
   in the `deviceInput` branch; `ChannelState::srcChan0` defaults to `-1`; `wz_engine.cpp:1145`
   reads `if (ch.srcChan0 == 1) → monitor else → main`. So `addLoopbackStrip(1)` produces a
   main tap. ~2 lines to fix (publish `srcChan0` for `busTap` from `source.id`).
2. **The master fader is not persisted.** `PatchSchema` has no master field; `MasterSection`
   holds the position in `useState`; `setMainFader` only does a `paramWrite`. Save, quit,
   reopen → the master returns to unity with no notice. Independent of everything in this
   document, and worth fixing regardless of which design wins.
3. **Only main and monitor have loopback snapshots.** Buses 1..7 have no previous-block
   buffer, so they cannot be tapped, cannot be resampled, and have no post-fader capture point
   for a future global record. `LOOPBACK_BUSES` in `patchValidation.ts` correctly refuses
   anything else — the refusal is honest, the gap is real.
4. **The watchdog guards bus 0 only.** `wdMeanSquare` integrates the main output; buses 1..7
   get `smMain` but no RMS detector and no limiter. `D-WZ-WATCHDOG-01` is phrased as *"a bus's
   RMS"*; the implementation is main-only. Fine for a stereo session, a gap for spatial.
5. **A strip cannot hold material and keep its source binding.** `usePatch.ts:40–44` rebinds a
   material-holding strip to `kind: 'deck'` at publish. This is a deliberate, documented
   trade (D-WZ-RECMODEL-01 step A) — but it is the mechanism that makes "a master strip can
   also loop" structurally impossible today, and it will bite again the first time any strip
   needs to be *both* a live input and a player. Worth a named decision eventually.
