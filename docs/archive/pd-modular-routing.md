# PD-MODULAR-ROUTING — "any strip can be a master": what it costs, and what to do

*Design analysis, 2026-07-24. Question posed: **the master stops being special — it is a
Strip whose source is a `busTap`, autogenerated at session start, and any strip could be
one.** This document answers whether the routing model survives that, and recommends.*

*Status: **analysis + recommendation, not yet a decision.** Nothing here is signed. It
touches D-WZ-ROUTINGVIEW-01, D-WZ-WATCHDOG-01 and the parked D-WZ-PDC-01; if adopted in
its full form it **revokes** D-WZ-ROUTINGVIEW-01 and **un-parks** D-WZ-PDC-01. Read §6
first if you only read one section.*

---

## 0. The finding in one paragraph

The proposal is really two proposals wearing one name, and they have opposite costs.
**"The master is a Strip"** is cheap, removes a real special case, and costs zero audio
latency — *provided the master strip's tap is resolved by render ORDER, not by the
one-block delay*. **"Any strip can be a master"** — general user-authored taps — is
expensive: it converts the star into a shallow mesh, makes the one-block delay
*accumulate*, introduces silent comb-filtering between parallel paths, moves the feedback
guard from "structurally impossible" to "structurally possible and only level-detected",
and forces the trace/cable layers that D-WZ-ROUTINGVIEW-01 and PD-MERGE §2 explicitly
refused. The first is a rendering and vocabulary change. The second is five specs of work.
They should not be adopted together, and only the first should be adopted now.

The load-bearing distinction, which the current model does not have a word for:

| | **tap-by-delay** (today's `busTap`) | **tap-by-order** (what a master/submix actually is) |
|---|---|---|
| reads | the bus's **previous** block snapshot | the bus's **current** block, after its contributors summed |
| latency | **+1 block** (10.7 ms @ 512/48k) | **0** |
| scheduling | none needed — acyclic *by construction* | needs a rank or a topological sort |
| cycles | possible, well-defined, **not refused** | must be **detected and refused** |
| honest name | a feedback/resample edge | a summing stage |

Today Wizard has exactly one tap kind (`busTap` = tap-by-delay) and uses it for exactly one
purpose (record-own-output). The proposal silently asks it to also mean tap-by-order. It
cannot mean both.

## 1. Does the star topology survive?

### 1.1 What the graph is today (verified in code)

- `engine/src/wz_engine.cpp:1181` — every strip sums into exactly one of
  `accBusL/R[0..7]` (`kMaxOutBuses = 8`, `engine/src/deck.h:29`), plus an independent cue
  accumulator via the `toMonitor` boolean. One hop. No strip reads another strip.
- `wz_engine.cpp:1141` — a `busTap` strip reads `loopbackMain*` / `loopbackMon*`, which
  `wz_engine.cpp:1304` fills at the **end** of the previous render, after the master fader
  and after the limiter. So the tap edge always crosses a block boundary.
- `web/src/engine/patchValidation.ts:35` — a `busTap` may name **bus 0 or bus 1 only**.
  The engine agrees: buses 2..7 have no loopback snapshot at all. **Tapping bus 3 is not a
  feature that exists today, in either layer.**

So: strips → buses (one hop, 8 destinations) + one delayed edge back from bus 0 or 1. A
star with one documented wormhole.

### 1.2 With tap-by-delay everywhere: still acyclic, but no longer a star

If `busTap` is generalised to all 8 buses and taps become common, the *acyclicity argument
survives untouched* — every tap edge is a block-boundary edge, so the intra-block schedule
is still "render all strips, then sum". `patchValidation.ts`'s comment ("there is no edge
type that can create a zero-delay cycle") stays literally true. **The invariant is not the
thing that breaks.**

What breaks is the *inference we drew from it*. The comment is doing double duty: it
justifies "no cycle detection needed" (still true) **and** it is quietly read as "the user
cannot build a runaway" (already false today, see §2.1; catastrophically false under
modular routing). The schedule stays acyclic; the **signal flow** becomes cyclic at block
rate. That is a delay-line feedback network, which is a perfectly good instrument and a
perfectly good disaster.

And topologically: bus *n* now has a strip audience, not just a device audience. The
one-hop reachability property — "a strip's bus chip tells you where it goes, full stop" —
is gone the moment two tap strips exist. It is not a mesh in the Max/MSP sense (still no
strip→strip edges), but it is a **layered star of unbounded depth**, which for a reader is
the same problem: you cannot answer "am I heard?" by looking at one object.

### 1.3 Trace: two masters, tap-by-delay

Session: strips `A` (deck), `B` (mic) → **bus 2**. Master `M` = `busTap(bus 2)` → bus 0
(device 1/2). Second master `N` = `busTap(bus 0)` → bus 3 (device 6/7 — an alternate PA
feed at a different level).

Block-by-block, `T` = one block:

| block | bus 2 contains | M outputs (reads bus 2 @ n−1) | bus 0 contains | N outputs (reads bus 0 @ n−1) | bus 3 contains |
|---|---|---|---|---|---|
| n | A,B(n) | A,B(n−1) | A,B(n−1) | A,B(n−2) | A,B(n−2) |
| n+1 | A,B(n+1) | A,B(n) | A,B(n) | A,B(n−1) | A,B(n−1) |

**Device 1/2 is 1 block late. Device 6/7 is 2 blocks late.** Latency is additive and
strictly one block per tap in the chain. At 512/48k that is 10.7 ms and 21.3 ms **on top
of** the device round-trip — and routing.md §6's proudest claim ("No buffering, no rings,
no latency added — input-to-output latency in P1 is exactly the device round-trip") is
retracted for every strip in the session, by a routing decision the performer made for a
different reason.

Now add the thing that will actually happen: strip `C` (a second mic) assigned **directly
to bus 0**, because that is the default. `C` reaches device 1/2 with **0** blocks of delay
while `A` and `B` reach it with **1**. If `A` and `C` are two mics on one source — or the
same deck fanned out for parallel processing — the sum is a **10.7 ms comb filter**. Not
an error. Not an alarm. It just sounds hollow, and nobody in a live room will diagnose it.
**This, not feedback, is the failure mode that will actually burn a user.** Today it is
structurally impossible (every path is exactly one hop). Under modular routing it is the
default outcome of an ordinary edit.

### 1.4 Trace: two masters, tap-by-order

Same session, but the taps read the current block. Now the render must be ordered: sum bus
2 → render M → sum bus 0 → render N → sum bus 3 → output. Zero added latency, no comb.
This is what the user actually wants and what every mixer does.

But now `patchValidation` must answer a question it has never had to answer: is
`M(bus 2) → bus 0`, `N(bus 0) → bus 3`, `P(bus 3) → bus 2` legal? It is a true zero-delay
cycle. It is trivially constructible with three clicks. The engine would either deadlock
the schedule or read a half-summed accumulator — **whichever it is, it is a bug class the
codebase currently cannot have.** Tap-by-order requires a genuine topological sort of the
strip set at publish time, a genuine cycle refusal in TS, and a documented answer for what
the engine does if a bad world ever reaches it (it must not trust TS blindly on the audio
thread; today it does not have to).

**Verdict on Q1:** the *acyclic-by-construction* sentence survives under tap-by-delay and
dies under tap-by-order. The *star* dies under both. The star is the more valuable of the
two properties, because it is the one the UI decision rests on (§3).

## 2. Feedback risk

### 2.1 The current model is already unguarded — it is just unpopulated

Two things are true today and worth stating plainly before judging the proposal:

1. A `busTap(bus 0)` strip assigned to `outBus 0` **is a unity-gain one-block feedback
   loop**, and `patchValidation` does not refuse it. The only thing standing between the
   user and a howl is `appStore.ts:290` — the loopback strip is **created muted**, with the
   comment *"an unmuted unity loopback of main is an instant sustained feedback path."*
   Default-mute is a good instinct and it is not a guard.
2. The watchdog watches **bus 0 only** (`wz_engine.cpp:1229`–`1270`: one leaky integrator
   over `accL`, the main accumulator). The limiter is applied **only** in the bus-0 sample
   loop. Buses 1..7 (`wz_engine.cpp:1281`) are multiplied by `smMain` and written straight
   to device channels — **no detector, no limiter, no alarm**. The cue bus is likewise
   unlimited.

So D-WZ-WATCHDOG-01's stated scope ("a bus's RMS") is **narrower in implementation than in
the decision text**: it is *the main bus's* RMS. Under today's topology that is nearly
complete coverage, because bus 0 is where nearly everything goes and the only tappable
buses are 0 and 1. Under "any strip can be a master" it is a hole you can drive a PA
through: a feedback loop living entirely in buses 3↔5 is inaudible to the watchdog and
unlimited on the way to the amplifier.

**This is the single hardest blocker.** Any version of this proposal that lets a tap name
a bus other than 0 or 1 **must** ship a per-bus detector + per-bus limiter first. Cost is
small (8 leaky integrators, 8 gain states, ~30 lines) and it is worth doing regardless of
this proposal, because it closes a live gap.

### 2.2 How many chained taps before it howls?

The number of taps is the wrong variable. A loop howls when **round-trip gain ≥ 1**;
chaining changes the *period*, not the *threshold*. What N taps buys you is a round-trip
time of N·T (N·10.7 ms @ 512/48k) instead of T, which changes the character from a rising
tone to a rising stutter/comb at 1/(N·T) Hz — and makes it *slower to detect*, not safer.

Rough arithmetic (**estimated, not measured — no test was run for this document**), signal
starting at −20 dBFS, one-block loop:

| loop gain per lap | laps to 0 dBFS | elapsed @ 512/48k |
|---|---|---|
| +1 dB | 20 | 213 ms |
| +3 dB | 7 | 75 ms |
| +6 dB | 4 | 43 ms |

Against a detector whose time constant is 250 ms. A one-pole integrator has reached only
~26 % of a step at 75 ms, so at the moment `wdMeanSquare` finally crosses +6 dBFS the
instantaneous level is already well past it — then the limiter takes another 10 ms
(`kRampSeconds`) to close. The overshoot is bounded and the limiter does eventually pin
the output, and the bus-0 loopback snapshot is taken **after** the limiter
(`wz_engine.cpp:1304`), so the loop is closed inside the limited path — that is a genuinely
good property of the current design and it should be preserved deliberately, not by
accident. But the honest statement is: **+6 dBFS/250 ms is a guard against a slow external
loop, not a fast internal one.**

### 2.3 The category error to avoid

D-WZ-WATCHDOG-01's rationale is explicit: *"External feedback loops are structurally
undetectable — the watchdog is the only guard."* That reasoning is sound **because internal
loops were impossible**. Under modular routing internal loops become possible *and remain
perfectly detectable* — they are visible in the Patch, at edit time, in TS, for free.
Leaning on the watchdog for them would be using a smoke alarm to enforce a building code.

**Internal feedback must be caught structurally at edit time. The watchdog stays what it
is: the guard for the loop we cannot see.** Both are needed; neither substitutes.

### 2.4 Does chaining latency multiply — and is that acceptable?

Yes, exactly N blocks for N chained tap-by-delay edges (§1.3). It is a **trap**, for three
reasons: (a) it is invisible at the point of the gesture — you assign a bus, you do not
"add 10.7 ms"; (b) it applies to a live monitoring path where 21 ms is the difference
between playable and not; (c) it is *unequal across parallel paths*, which is the comb
problem of §1.3 and is worse than uniform latency in every way. A performer can adapt to
latency. Nobody adapts to a notch at 47 Hz that appears when you re-assign a bus.

## 3. Comprehensibility — the real risk

D-WZ-ROUTINGVIEW-01's rationale is a conditional: *"Wizard's graph is a STAR (each strip →
one of 8 buses), not a mesh; drawing cables would picture a topology the app does not
have."* pd-plane-playground §3.1 states the same premise and derives **R-ROUTE-1: no
general cable layer — "not on by default, not as an option, not later"** — from it. PD-MERGE
§2 then refuses the hold-to-trace highlight, the bus rail and the matrix-as-overlay on the
same ground.

**If the graph stops being a star, the premise of that decision is false and the decision
is unsupported.** That must be said plainly: *this proposal, in its general form, costs us
D-WZ-ROUTINGVIEW-01.*

Concretely, what the chip stops being able to answer:

- **"Where does this go?"** The chip says `▸2`. Under modular routing bus 2's audience is a
  strip somewhere else on a boundless plane, at some scroll position, possibly off-screen.
  The chip's answer is now the first token of an answer.
- **"Am I heard?"** — the question that actually matters at 22:00 with an audience. Today
  it is a lookup: is my bus mapped to a device output? (pd-strip-anatomy state 15 does
  exactly this, and PD-MERGE §5's *"No silent silence"* law demands it.) Under modular
  routing it is a **reachability walk**: bus 2 → M → bus 0 → device. If M is muted, A and B
  are silent and **nothing on A or B says so.** A whole subtree goes dark because of a
  mute on an object that is not on screen. This is the failure the "no silent silence" law
  exists to prevent, and modular routing reintroduces it in a form the current UI cannot
  express.
- **"Why does this sound thin?"** Not answerable by any per-object label at all (§1.3).

pd-plane-playground §3.3's **R-ROUTE-2** already grants an exception: the loopback edge is
the one persistent connector drawn on the plane, *"the exception that proves R-ROUTE-1"*.
An exception for one edge in a session is a highlight. An exception for the *general* case
is a cable layer with extra steps. There is no honest middle: **if taps are general, the
trace layer (hold-to-trace highlight + bus rail) stops being deferred chrome and becomes
the minimum viable explanation.** That is roughly the work PD-MERGE §2 declined, pulled
forward, plus a new "audibility" state on the Strip.

Master-as-strip-**only** does not have this problem: one blessed tap, known at session
start, always present, always in the same conceptual place. The chip stays true, R-ROUTE-2
already covers drawing it, and the performer's model is unchanged — "strips go to buses,
buses go out, and the master is the one that goes out."

## 4. Latency accounting

playback-composer §2 is normative: *"Cost: exactly one block of latency on the loopback
path (at 512/48k, 10.7 ms). That is the honest price and it is stated in the UI, not
hidden."* pd-strip-anatomy state 16 implements it as a status line: `↺ +N.N ms (one
block)`.

That sentence is written for **one** edge. Under chained taps it has three problems:

1. **"one block" becomes a lie.** The literal string must go; the number must be computed.
2. **The price is no longer paid by the strip that shows it.** A tap strip's own delay is
   one block; the delay experienced by *A and B feeding it* is one block too — and they say
   nothing. The honest display is **per-strip accumulated latency to the device**, not
   per-edge latency at the tap.
3. **The number differs between siblings**, which is the comb problem. The dangerous fact
   is not "this path is 21 ms", it is "**these two paths differ by 10.7 ms**".

If general taps ship, the following are required, not optional:

- `latencySamples` computed **per strip, at publish time, in TS** (the document owner
  computes it; the engine does not discover it) — a simple longest-path walk over
  strip→bus→tap-strip edges. Cheap, no ABI change if it stays UI-side; needs an ABI field
  only if the engine must compensate.
- Displayed **on the object** (pd-strip-anatomy's own rule: a strip that is silent or
  delayed for a routing reason says so without being selected), as accumulated ms, not
  block count.
- A **session-level max/spread** readout in the routing matrix — the spread is the warning
  value.
- **D-WZ-PDC-01 stops being parked.** It is currently deferred to P6 on the grounds that
  inserts are what create unequal path latency. Modular routing creates unequal path
  latency in P4 with no inserts at all. Either we compensate parallel paths (the parked
  proposal's own preferred option) or we accept audible combing as a documented
  consequence. Adopting general modular routing without answering D-WZ-PDC-01 first would
  be shipping a known audio-quality defect.

## 5. Guards

**Essential** (none of these is optional if a tap can name any bus):

| # | Guard | Why essential |
|---|---|---|
| G1 | **Per-bus watchdog + per-bus limiter** (all 8 + cue), replacing the bus-0-only implementation | §2.1. Today a runaway on bus 3 is undetected *and* unlimited into the amplifier. Blocker. |
| G2 | **Edit-time self-loop refusal**: refuse a tap whose tapped bus is reachable from the tapping strip's own output bus | §2.3 — internal loops are detectable, so detect them. Must include the trivial case that is already constructible today (`busTap(0) → outBus 0`). |
| G3 | **"Not heard" state on the Strip**: bus reaches no mapped device output, or reaches it only through a muted/soloed-away tap | §3. PD-MERGE §5 "No silent silence" is already law; modular routing breaks it unless this exists. |
| G4 | **Accumulated latency on the object + spread warning** | §4. The comb is silent and undiagnosable otherwise. |
| G5 | **Max tap depth**, hard-refused at edit time | Bounds latency, bounds the reachability walk, bounds the UI. Proposal: **2** for a modular model (one submix layer + master), **1** for master-only. Arbitrary but cheap, and an arbitrary bound the user can see beats an unbounded one they cannot. |

**Nice, in priority order:** hold-to-trace highlight (from pd-plane-playground §3.2 L1, the
first thing to un-defer if G3's per-object label proves too weak); a routing-matrix column
showing accumulated latency per strip; a distinct visual for "this strip's tap is
deliberately a feedback edge" versus "this strip's tap is a summing stage" (if both kinds
exist, they must not look alike); a confirm-on-create for a deliberate feedback tap that
G2 would otherwise refuse — because record-own-output *is* a wanted feedback edge and G2
must not make Wizard's differentiator unbuildable.

Note the tension between G2 and the LoopbackBus: the one legal cycle **is** the case G2
refuses. Resolution: G2 refuses **silently-created** and **autogenerated** taps absolutely,
and downgrades to an explicit confirmation for a user-authored tap-by-delay strip, which is
then created muted (as it already is) and is the one object allowed to close a loop. If the
two tap kinds of §0 are made explicit in the schema, this falls out cleanly: **tap-by-order
may never close a loop; tap-by-delay may, with consent.**

## 6. Simpler or more complex? — recommendation

### What the proposal genuinely wins

It is not nothing, and the pull is real:

- **It satisfies "everything is a channel."** MORNING-DECISIONS records the load-bearing
  finding that `Channel` is *already* the one strip type and one-object-type is a rendering
  change, not a data-model change. PD-MERGE §1 then carves out an exception in prose:
  *"Master strip … it is not a Strip on the map because it is the destination, not a
  source."* That sentence is the special case, and the proposal deletes it.
- **It fixes a real incoherence in the engine.** `smMain` is applied to bus 0 **and** to
  buses 1..7 (`wz_engine.cpp:1288`), so today's "master fader" is secretly a global output
  trim on all eight buses, while only bus 0 gets metering, a limiter and a fader UI. Buses
  1..7 have no fader, no mute, no meter and no owner. That is worse than a special case —
  it is an unstated one. Giving each bus an owning strip fixes it.
- **It gives 8 output buses the strip anatomy they already deserve** (meter, fader, mute,
  cue lamp, status line), with zero new UI vocabulary.

### What it costs, by option

**Option A — full modular** (general user-authored taps, any strip can tap any bus):
star → layered graph; comb filtering by default; per-bus watchdog required; latency
accounting required; D-WZ-PDC-01 un-parked; **D-WZ-ROUTINGVIEW-01 revoked** and the trace
layer PD-MERGE §2 refused pulled forward; a new routing model the performer must learn. Set
against the standing instruction *"keep it simple before we expand too much and clutter the
code"* and PD-MERGE's own rule *"no new surface, no new persisted field, unless one of the
four surfaces cannot work without it"* — this is precisely the clutter that instruction was
written to prevent. **Reject for this phase.**

**Option C — keep the special master**: costs nothing, changes nothing, leaves the
`smMain`-on-all-buses incoherence and the prose exception in PD-MERGE §1 standing. Safe,
and slightly dishonest.

**Option B — master-as-strip only. Recommended.**

Concretely, and this is the whole proposal:

> A **bus-owner strip** is an ordinary Strip whose source is its bus's **current-block** sum
> (tap-by-order, §0). One per output bus, **autogenerated at session start**, not
> user-created and not deletable. It carries fader, pan, mute, cue and meters like any
> Strip. **Its output goes to the device map — never to another bus.**

That one rule ("never to another bus") is what buys everything:

- **Zero added latency.** No block delay anywhere; routing.md §6's round-trip claim stands.
- **Cycles remain impossible by construction**, for a *new* reason that is just as simple as
  the old one and can be stated in one line in `patchValidation.ts`: a bus-owner strip has
  no outgoing bus edge, so the graph is two ranks deep and can never close. No topological
  sort, no cycle detection, no audio-thread trust problem.
- **Still a star** — strips → bus → the bus's own strip → device. Every strip still has
  exactly one outgoing edge to exactly one bus. **D-WZ-ROUTINGVIEW-01 survives intact**; the
  chip's answer is still complete, because the chip names the bus and the bus now visibly
  *has a face*.
- **"Everything is a channel" becomes true** and PD-MERGE §1's prose exception is deleted:
  the master strip is a Strip; it is merely pinned rather than freely placed (that is a
  layout fact, not a type fact, and the plane already has pinned placement in PD-MERGE-03).
- **`busTap` keeps its current meaning, unchanged** — the one blessed tap-by-delay edge for
  record-own-output, buses 0/1 only, created muted, drawn with R-ROUTE-2's curved arrow and
  its honest `+10.7 ms`. Nothing about §2's feedback story changes.
- **Cost:** the engine renders bus-owner strips in a second pass after the bus sums —
  structurally the same loop that already applies `smMain`, so it is a refactor of existing
  code rather than new machinery. Schema: a `busOwner: n` marker on Channel plus a migration
  that mints the strips; the existing per-channel params carry everything else.
- **G1 (per-bus watchdog + limiter) should ship with it** — not because Option B creates the
  risk, but because Option B is the increment that finally gives buses 1..7 an owner, and
  shipping an owner without a limiter is worse than shipping neither. G3 and G5 are not
  needed under Option B (depth is fixed at 2; "not heard" stays the existing unmapped-chip
  lookup plus "my bus's owner is muted", which is a one-hop check).

**If submixes are later genuinely wanted**, the smallest honest extension is to let a
bus-owner strip output into a bus of **strictly lower index** — that yields a static render
order (bus 7's owner, then 6, … then 0's), still zero latency, still no possible cycle, no
sort, depth bounded by 8. It is worth knowing that door exists. It should stay shut until
someone has actually hit the wall, because it makes bus *index* meaningful — a hidden rule
the chip would then have to teach.

### Recommendation

**Adopt Option B (master-as-strip, one bus-owner strip per output bus, tap-by-order, no
general modular routing). Ship G1 with it. Do not adopt Option A.** Option B takes the
proposal's real win — deleting the master's special case and satisfying "everything is a
channel" — at zero latency cost, zero risk to D-WZ-ROUTINGVIEW-01, and no new routing model
for the performer to learn. Option A buys flexibility nobody has yet asked for, in exchange
for the two properties that make Wizard's UI defensible: **one hop, and no hidden latency.**

## 7. Unverified / flagged

- **No build or test was run for this document.** All latency figures are arithmetic
  (block/48000) and all feedback growth figures in §2.2 are estimates from loop gain, not
  measurements. If Option A were ever seriously considered, `loopback_test` and
  `watchdog_test` should be extended to measure chained-tap growth before, not after.
- Host block size was not confirmed; **512 frames @ 48 kHz = 10.667 ms is assumed
  throughout** because playback-composer §2 uses it. `AudioIO.cpp` sets the device setup
  from the picker, so the real figure is device-dependent and every "+10.7 ms" in the UI
  must be computed from the live block size, not a constant.
- The claim that buses 1..7 are unlimited and unwatched is read from `wz_engine.cpp`
  (detector and limiter appear only in the bus-0 sample loop at 1229–1270; the 1..7 loop at
  1281–1297 applies `smMain` only). Worth a deliberate confirmation before it is treated as
  a shipped defect — but if it holds, it is one, independent of this proposal.
- Whether `wz_engine_render_io`'s caller guarantees `bus_out` channel ordering matches the
  `2b+2` mapping assumed at `wz_engine.cpp:1282` was not traced into the host.
- Engine work for Option B is estimated as "a refactor of the existing `smMain` pass"; that
  is a reading of the code, not a costed plan.
